🎯 1. Visão Geral da Arquitetura

1.1 Objetivo do Documento

Este Software Architecture Document (SAD) define a arquitetura de software do Projeto MAFFENG, um ecossistema integrado de automação técnica. O documento serve como guia técnico definitivo para desenvolvedores, arquitetos e stakeholders, descrevendo padrões arquiteturais, decisões técnicas, componentes do sistema e suas interações.

1.2 Escopo do Sistema

O ecossistema MAFFENG é composto por três módulos principais integrados:

📱 App Mobile (Levantamentos)
Aplicativo React Native para captura fotográfica em campo, coleta de medições e observações técnicas offline-first.
💼 Gerenciador de O.S.
Sistema web React para gestão de ordens de serviço, atribuição de técnicos, upload de pacotes e rastreabilidade completa.
📊 Auto Relatórios
Motor de geração automática de relatórios técnicos em PDF com templates personalizáveis e integração com dados coletados.

1.3 Objetivos Arquiteturais

A arquitetura do sistema MAFFENG foi projetada para atender os seguintes objetivos:

Objetivo Descrição Métrica de Sucesso
Modularidade Módulos independentes que podem evoluir separadamente Deploy independente de cada módulo
Escalabilidade Suporte para crescimento de usuários e dados Suportar 1000+ usuários simultâneos
Segurança Proteção de dados sensíveis e autenticação robusta Conformidade com LGPD e zero vazamentos
Performance Resposta rápida e experiência fluida API < 500ms (p95), FCP < 2s

🔐 4. Autenticação e Autorização

4.1 Fluxo de Autenticação (JWT)

1. Login do Usuário
Usuário fornece email e senha através do formulário de login. Cliente React/React Native envia credenciais via Supabase Client.
2. Validação no Supabase Auth
Supabase Auth valida credenciais contra tabela auth.users. Se válido, gera JWT access token (1h) + refresh token (30d).
3. Retorno de Tokens
Tokens são retornados ao cliente e armazenados de forma segura (httpOnly cookie para web, SecureStore para mobile).
4. Requisições Autenticadas
Todas as requisições subsequentes incluem JWT no header Authorization: Bearer {token}. Supabase valida token automaticamente.
5. Refresh Token
Quando access token expira (1h), cliente automaticamente usa refresh token para obter novo access token sem re-login.

4.2 Row Level Security (RLS)

Todas as tabelas do banco de dados possuem políticas RLS que garantem isolamento de dados:

-- Exemplo: Política de SELECT para ordens_servico
CREATE POLICY "os_select_policy" ON ordens_servico
FOR SELECT USING (
  auth.uid() IN (
    SELECT user_id FROM users_permissions
    WHERE permission IN ('os.read', 'admin')
  )
);

-- Técnicos só veem suas próprias O.S.
CREATE POLICY "os_tecnico_policy" ON ordens_servico
FOR SELECT USING (tecnico_id = auth.uid());

4.3 Matriz de Permissões (RBAC)

O sistema implementa controle de acesso baseado em papéis (Role-Based Access Control):

Perfil Ordens de Serviço Usuários Relatórios Configurações
Admin CRUD completo CRUD completo Visualizar todos CRUD completo
Gestor CRUD (suas equipes) Read (suas equipes) Visualizar (suas equipes) Read only
Técnico Read + Update status Read (próprio perfil) Visualizar (próprias) Nenhum
Cliente Read (próprias) Nenhum Visualizar (próprias) Nenhum
Visualizador Read only Nenhum Visualizar (permitidas) Nenhum

4.4 Segurança Adicional

🔒 HTTPS Obrigatório
Todas as comunicações entre cliente e servidor usam TLS 1.3+. Certificados SSL gratuitos via Vercel/Let's Encrypt com renovação automática.
🛡️ CORS Configurado
Supabase configurado para aceitar requisições apenas de domínios autorizados (whitelist). Proteção contra ataques CSRF.
🔐 Senhas Hash
Senhas armazenadas com bcrypt (cost factor 10+). Nunca expostas em logs ou respostas de API.
⏱️ Rate Limiting
Proteção contra brute force: máximo 5 tentativas de login a cada 15 minutos por IP. APIs limitadas a 100 req/min por usuário.
📝 Audit Logs
Todas as ações críticas (criação de O.S., mudança de status, exclusões) são registradas em tabela de auditoria com timestamp e user_id.

5.4 Triggers e Stored Procedures

-- Trigger: Atualiza updated_at automaticamente
CREATE TRIGGER update_os_timestamp
BEFORE UPDATE ON ordens_servico
FOR EACH ROW EXECUTE FUNCTION update_timestamp();

-- Function: Calcula progresso de O.S.
CREATE FUNCTION calcular_progresso_os(os_id UUID)
RETURNS INTEGER AS $
  SELECT (COUNT(*) FILTER (WHERE status = 'concluido') * 100)
    / NULLIF(COUNT(*), 0)
  FROM ambientes WHERE ordens_servico_id = os_id;
$ LANGUAGE SQL;

🔄 6. Fluxos de Dados Principais

6.1 Fluxo: Criação de Ordem de Serviço

1. Gestor acessa Gerenciador O.S.
Interface web exibe formulário de criação com campos: cliente, endereço, tipo de serviço, técnico responsável, prazo.
2. Validação Frontend
React valida campos obrigatórios, formato de dados, datas. Exibe erros em tempo real.
3. Envio para API
POST /api/ordens-servico com payload JSON. Supabase Client adiciona JWT automaticamente no header.
4. Validação Backend + RLS
Supabase valida JWT, verifica permissões via RLS policies. Se aprovado, insere registro na tabela ordens_servico.
5. Notificação Realtime
Supabase Realtime envia notificação via WebSocket para técnico atribuído. App mobile recebe push notification.
6. Confirmação ao Cliente
API retorna O.S. criada com ID gerado. Frontend exibe mensagem de sucesso e redireciona para detalhes da O.S.

6.2 Fluxo: Captura Fotográfica em Campo (Offline-First)

1. Técnico seleciona ambiente
App mobile exibe lista de ambientes da O.S. sincronizada previamente. Técnico pode estar offline.
2. Captura de foto
App abre câmera nativa via Expo Camera. Foto capturada é salva localmente em alta resolução (3-5MB).
3. Armazenamento Local
Foto é armazenada em AsyncStorage com metadata: ambiente_id, timestamp, geolocalização, observação. Status: "pending_upload".
4. Detecção de Conectividade
App monitora conectividade via NetInfo. Quando online, queue de upload é ativada automaticamente.
5. Upload Assíncrono
Fotos são enviadas para Supabase Storage via upload chunked (5MB/chunk). Barra de progresso exibe status.
6. Registro no Banco
Após upload bem-sucedido, registro é criado na tabela fotos com storage_path. Foto local é marcada como "uploaded" e pode ser deletada.

6.3 Fluxo: Geração de Relatório Técnico

1. Solicitação de Relatório
Gestor acessa Gerenciador O.S., seleciona O.S. concluída e clica em "Gerar Relatório". Escolhe template (Padrão, Detalhado, Executivo).
2. Coleta de Dados
Backend busca todos os dados relacionados: O.S., ambientes, fotos, medições, observações. Dados são agregados em estrutura JSON.
3. Geração do PDF
Motor de relatórios (biblioteca PDFKit ou jsPDF) processa template escolhido. Imagens são comprimidas e inseridas. Layout responsivo ajusta número de páginas.
4. Upload do PDF
PDF gerado é enviado para Supabase Storage em bucket "relatorios". Nome do arquivo: {numero_os}_{timestamp}.pdf.
5. Notificação e Download
Link do PDF é retornado ao frontend. Gestor recebe notificação e pode baixar/visualizar/enviar por email. Cliente também pode acessar via portal.

7.2 Exemplo: Store Zustand (Autenticação)

// stores/authStore.js
import create from 'zustand';
import { supabase } from '../lib/supabase';

export const useAuthStore = create((set) => ({
  user: null,
  session: null,
  loading: true,

  signIn: async (email, password) => {
    const { data, error } = await supabase.auth.signInWithPassword({
      email, password
    });
    if (data) set({ user: data.user, session: data.session });
    return { data, error };
  },

  signOut: async () => {
    await supabase.auth.signOut();
    set({ user: null, session: null });
  }
}));

7.3 Cache e Invalidação (React Query)

// hooks/useOrdensServico.js
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';

export function useOrdensServico() {
  const queryClient = useQueryClient();

  // Query com cache de 5 minutos
  const { data, isLoading } = useQuery({
    queryKey: ['ordens-servico'],
    queryFn: fetchOrdensServico,
    staleTime: 5 * 60 * 1000
  });

  // Mutation com invalidação automática
  const createMutation = useMutation({
    mutationFn: createOS,
    onSuccess: () => {
      queryClient.invalidateQueries(['ordens-servico']);
    }
  });

  return { data, isLoading, createOS: createMutation.mutate };
}

🎯 10. Architecture Decision Records (ADRs)

Decisões arquiteturais importantes documentadas para rastreabilidade e contexto:

ADR-001: Escolha de Supabase como Backend
✅ ACEITO
Contexto: Necessidade de backend escalável com auth, database e storage integrados.

Decisão: Adotar Supabase como Backend-as-a-Service principal.

Justificativa: Reduz tempo de desenvolvimento em 60%, elimina necessidade de gerenciar infraestrutura, oferece RLS nativo para segurança, possui cliente JavaScript/TypeScript maduro, comunidade ativa e documentação excelente.

Consequências: ✅ Desenvolvimento mais rápido | ✅ Segurança robusta via RLS | ⚠️ Vendor lock-in (mitigado com PostgreSQL standard) | ⚠️ Custo crescente com escala (planejado no roadmap)
ADR-002: React Native + Expo para Mobile
✅ ACEITO
Contexto: Necessidade de aplicativo mobile cross-platform com acesso a câmera e funcionalidade offline.

Decisão: Usar React Native com Expo Managed Workflow.

Justificativa: Desenvolvimento único para iOS e Android, acesso a APIs nativas via Expo modules, OTA updates sem app store review, comunidade gigante e reuso de conhecimento React do web.

Consequências: ✅ Time-to-market reduzido | ✅ Manutenção unificada | ⚠️ Performance ligeiramente inferior ao nativo puro (aceitável para caso de uso) | ⚠️ Dependência de Expo (mitigado com possibilidade de eject)
ADR-003: Offline-First para App Mobile
✅ ACEITO
Contexto: Técnicos trabalham em ambientes com conectividade limitada ou instável.

Decisão: Implementar estratégia offline-first com sync automático quando online.

Justificativa: Garante produtividade independente de rede, reduz frustração do usuário, evita perda de dados, melhora UX com feedback imediato.

Consequências: ✅ UX superior | ✅ Maior confiabilidade | ⚠️ Complexidade adicional no código | ⚠️ Necessidade de resolver conflitos de sincronização | ⚠️ Armazenamento local maior
ADR-004: React Query para Server State
✅ ACEITO
Contexto: Necessidade de gerenciar estado servidor com cache, refetch e sincronização.

Decisão: Usar TanStack React Query como camada de gerenciamento de estado servidor.

Justificativa: Cache automático e inteligente, invalidação declarativa, retry logic, loading/error states padronizados, DevTools excelente, reduz boilerplate em 70%.

Consequências: ✅ Código mais limpo | ✅ Performance melhorada | ✅ Menos bugs de sincronização | ⚠️ Curva de aprendizado inicial | ✅ Padrão da indústria
ADR-005: Zustand para Estado Global Cliente
✅ ACEITO
Contexto: Necessidade de estado global leve para auth, tema e configurações.

Decisão: Usar Zustand em vez de Redux ou Context API puro.

Justificativa: API minimalista (< 50 linhas de código), zero boilerplate, performance superior (sem re-renders desnecessários), TypeScript-first, middleware integrado.

Consequências: ✅ Simplicidade extrema | ✅ Bundle size mínimo (1KB) | ✅ Fácil onboarding | ⚠️ Menos "opinativo" que Redux | ✅ Ideal para escopo do projeto
ADR-006: Monorepo vs Multirepo
✅ ACEITO - Multirepo
Contexto: Três módulos principais (Mobile, Gerenciador, Auto Relatórios) precisam de estrutura de repositório.

Decisão: Usar estratégia multirepo com repositórios separados por módulo.

Justificativa: Deploy independente por módulo, CI/CD mais simples, permissões de acesso granulares, menor complexidade de build, alinhado com arquitetura de microserviços.

Consequências: ✅ Independência total | ✅ Deploys isolados | ⚠️ Código compartilhado requer npm packages | ⚠️ Sincronização manual de dependências | ✅ Escalabilidade de equipe
ADR-007: TypeScript como Opcional (Fase Futura)
✅ ACEITO
Contexto: Necessidade de tipagem estática vs velocidade de desenvolvimento inicial.

Decisão: Iniciar com JavaScript + JSDoc e migrar para TypeScript na Fase 2 de maturação.

Justificativa: Time atual mais produtivo em JS, prototipagem mais rápida, reduz complexidade inicial, migração incremental possível com JSDoc types.

Consequências: ✅ Velocidade inicial maior | ⚠️ Menos segurança de tipos (mitigado com JSDoc) | ✅ Flexibilidade para experimentação | 📅 Migração para TS planejada para Q2 2026

* @param {boolean} props.disabled - Botão desabilitado
*/
export function ButtonPrimary({ label, onClick, loading, disabled }) {
  return (
    <button
      className="btn-primary"
      onClick={onClick}
      disabled={disabled || loading}
    >
      {loading ? 'Carregando...' : label}
    </button>
  );
}

🔄 14. Backup e Disaster Recovery

14.1 Estratégia de Backup

Tipo de Dado Frequência Retenção Localização
Database (PostgreSQL) Diário (automático) 30 dias Supabase (multi-region)
Storage (Fotos/PDFs) Contínuo (S3 versioning) 90 dias Supabase Storage + Glacier
Código-fonte Cada commit Indefinido GitHub (cloud backup)
Configurações Cada mudança Indefinido Git (infra-as-code)

14.2 Recovery Time Objective (RTO)

Tempo máximo aceitável para restauração após incidente:

Cenário 1 - Falha de Aplicação: RTO = 15 minutos
  → Rollback automático para versão anterior no Vercel

Cenário 2 - Corrupção de Dados: RTO = 2 horas
  → Restauração de backup diário do Supabase

Cenário 3 - Falha Completa de Infraestrutura: RTO = 4 horas
  → Migração para novo projeto Supabase + redeploy

14.3 Recovery Point Objective (RPO)

Perda máxima de dados aceitável:

Banco de Dados: RPO = 24 horas
  → Backup diário às 03:00 AM (horário de menor uso)

Storage (Fotos): RPO = 0 (zero data loss)
  → Replicação síncrona S3 + versionamento ativado

Código: RPO = 0 (zero data loss)
  → Git distributed version control

14.4 Plano de Disaster Recovery

1. Detecção do Incidente
Alertas automáticos via Sentry/Uptime Robot detectam falha. On-call engineer é notificado via PagerDuty.
2. Avaliação de Impacto
Engineer avalia severidade (P0-P4). P0/P1 acionam protocolo de emergência com comunicação imediata para stakeholders.
3. Ação Corretiva
Dependendo do tipo de falha: rollback de deploy, restauração de backup, failover para standby, ou hotfix emergency.
4. Validação
Testes de smoke realizados para confirmar restauração. Monitoramento intensivo por 24h.
5. Post-Mortem
Documento post-mortem criado dentro de 48h. Root cause analysis, ações corretivas, melhorias de processo.

🔐 16. Segurança e Compliance

16.1 Medidas de Segurança Implementadas

🔒 Criptografia em Trânsito
TLS 1.3 obrigatório para todas as conexões. Certificados SSL com renovação automática. HSTS enabled com max-age de 1 ano.
🗄️ Criptografia em Repouso
PostgreSQL com encryption at rest (AES-256). Supabase Storage usa S3 server-side encryption. Backups criptografados.
🔐 Gestão de Secrets
Variáveis de ambiente nunca commitadas no Git. Supabase vault para secrets sensíveis. Rotação de API keys a cada 90 dias.
🛡️ Proteção contra Ataques
SQL Injection: prevenido via prepared statements e RLS. XSS: sanitização automática no React. CSRF: tokens em formulários sensíveis. DDoS: Vercel/Cloudflare rate limiting.
👤 Privacidade de Dados
LGPD compliance: consentimento explícito, direito de exclusão, portabilidade de dados. Dados pessoais minimizados. Logs anonimizados após 90 dias.
📝 Auditoria
Audit logs para todas as ações críticas. Retention de 2 anos. Logs imutáveis (append-only). Acesso restrito a admins.

🔄 18. Comunicação entre Módulos

18.1 Integração: Mobile ↔ Gerenciador O.S.

Fluxo de Comunicação Mobile-to-Web
📱 ↔ 💻

18.2 Integração: Gerenciador O.S. ↔ Auto Relatórios

1. Trigger de Geração
Gestor clica em "Gerar Relatório" no Gerenciador. Request enviada via API: POST /api/relatorios/gerar com os_id.
2. Coleta de Dados
Backend busca todos os dados relacionados: O.S., ambientes, fotos (URLs), medições, observações. Aggregação em JSON estruturado.
3. Chamada ao Motor de Relatórios
API interna chama serviço Auto Relatórios com payload completo. Motor seleciona template e renderiza PDF.
4. Upload e Notificação
PDF gerado é enviado para Supabase Storage. URL é retornada. Notificação via Realtime atualiza Gerenciador.
