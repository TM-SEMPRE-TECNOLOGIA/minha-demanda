1. Visão Geral do Produto

1.1 Declaração do Problema

Empresas de engenharia, manutenção e fiscalização enfrentam desafios críticos na gestão de ordens de serviço:

  • Falta de visibilidade em tempo real do status das O.S.
  • Processos manuais para importação e distribuição de tarefas
  • Dificuldade em rastrear o ciclo de vida completo das ordens
  • Dados fragmentados entre múltiplas ferramentas
  • Retrabalho na validação de levantamentos fotográficos
  • Falta de integração entre campo e escritório
  • Dificuldade em cumprir SLAs contratuais

1.2 Proposta de Solução

TM Gerenciador de O.S. é o núcleo central do Ecossistema MAFFENG, responsável por:

  • Centralizar a gestão completa de ordens de serviço
  • Receber e validar pacotes de levantamentos fotográficos do app mobile
  • Encaminhar dados validados para o TM Auto Relatórios
  • Consolidar métricas para o TM Painel do Diretor
  • Garantir rastreabilidade total do fluxo técnico

1.3 Objetivos de Negócio

Eficiência Operacional
Reduzir em 60% o tempo de gestão manual de O.S. através de importação em lote e automação de fluxos
Visibilidade Total
Fornecer visibilidade em tempo real de 100% das O.S. em andamento com dashboards atualizados
Qualidade de Dados
Garantir 95%+ de precisão nos dados através de validação estruturada e checklist obrigatório
Cumprimento de SLA
Aumentar em 40% a taxa de cumprimento de prazos contratuais com alertas proativos

1.4 Métricas de Sucesso

Métrica Meta Prazo
Tempo médio de importação de O.S. < 5 minutos para 100 O.S. MVP
Taxa de adoção por gerentes > 90% dos gerentes ativos Mês 3
Precisão de dados validados > 95% sem retrabalho Mês 6
Redução de tempo de validação -50% vs. processo manual Mês 6
NPS (Net Promoter Score) > 50 Mês 12

2.2 Casos de Uso Principais

UC-01: Importação de Ordens de Serviço

Ator: Gerente de Contrato

Pré-condições: Planilha Excel válida com O.S. do cliente

Fluxo Principal:

  1. Gerente acessa módulo de importação
  2. Faz upload de planilha Excel (.xlsx)
  3. Sistema valida estrutura e dados obrigatórios
  4. Sistema exibe preview das O.S. a serem importadas
  5. Gerente confirma importação
  6. Sistema cria registros no banco de dados
  7. Sistema notifica sucesso e exibe O.S. importadas

Pós-condições: O.S. criadas com status "Pendente"

CRÍTICO
UC-02: Distribuição de O.S. para Técnicos

Ator: Gerente de Contrato

Pré-condições: O.S. importadas e técnicos cadastrados

Fluxo Principal:

  1. Gerente visualiza lista de O.S. pendentes
  2. Seleciona uma ou múltiplas O.S.
  3. Escolhe técnico(s) disponível(is)
  4. Sistema atualiza status para "Atribuída"
  5. Sistema notifica técnico no app mobile
  6. Técnico recebe O.S. no TM Levantamentos

Pós-condições: O.S. visível no app mobile do técnico

CRÍTICO
UC-03: Recebimento de Pacote de Levantamento

Ator: Sistema (automático)

Pré-condições: Técnico finalizou captura no app mobile

Fluxo Principal:

  1. App mobile envia pacote ZIP via HTTPS (POST /api/upload-pacote)
  2. Sistema valida integridade do arquivo
  3. Sistema extrai conteúdo: fotos + JSON + metadados
  4. Sistema valida estrutura do JSON
  5. Sistema associa pacote à O.S. correspondente
  6. Sistema atualiza status para "Aguardando Validação"
  7. Sistema notifica gerente responsável

Pós-condições: Pacote armazenado e disponível para validação

CRÍTICO
UC-04: Validação de Pacote de Levantamento

Ator: Gerente de Contrato

Pré-condições: Pacote recebido e aguardando validação

Fluxo Principal:

  1. Gerente acessa fila de validação
  2. Seleciona pacote para revisar
  3. Sistema exibe galeria de fotos + dados coletados
  4. Gerente revisa qualidade das fotos
  5. Gerente verifica completude das informações
  6. Gerente aprova ou rejeita com motivo
  7. Se aprovado: Sistema encaminha ao TM Auto Relatórios
  8. Se rejeitado: Sistema notifica técnico para retrabalho

Pós-condições: Pacote aprovado ou devolvido

CRÍTICO
UC-05: Monitoramento de SLA

Ator: Gerente de Contrato

Pré-condições: O.S. com prazos definidos

Fluxo Principal:

  1. Gerente acessa dashboard de SLA
  2. Sistema calcula tempo decorrido vs. prazo contratual
  3. Sistema exibe O.S. em risco (prazo < 20% restante)
  4. Sistema envia alertas automáticos para O.S. críticas
  5. Gerente pode filtrar por status, técnico ou contrato
  6. Gerente toma ações corretivas (realocar, priorizar)

Pós-condições: Riscos identificados e ações tomadas

5. Arquitetura Técnica

5.1 Stack Tecnológico

Frontend
  • Framework: React 18+ com TypeScript
  • Build Tool: Vite
  • Estilização: Tailwind CSS + Design System TM
  • Estado: React Context API + Zustand
  • Roteamento: React Router v6
  • Validação: Zod + React Hook Form
Backend
  • BaaS: Supabase (PostgreSQL)
  • Autenticação: Supabase Auth (JWT)
  • Storage: Supabase Storage (fotos)
  • Real-time: Supabase Realtime (WebSocket)
  • APIs: Supabase Edge Functions
  • Processamento: Python + FastAPI (Auto Relatórios)

5.2 Modelo de Dados (Resumo)

Entidades Principais:

  • contracts - Contratos com clientes
  • service_orders - Ordens de serviço
  • packages - Pacotes de levantamento fotográfico
  • photos - Fotos individuais dos pacotes
  • users - Usuários do sistema (gerentes, técnicos)
  • reports - Relatórios gerados pelo TM Auto Relatórios
  • logs - Logs de auditoria e integração

Relacionamentos: Ver DER completo já documentado na Fase 1

5.3 Endpoints REST (Principais)

Método Endpoint Descrição
POST /api/service-orders/import Importa O.S. via Excel
POST /api/service-orders Cria O.S. manual
GET /api/service-orders Lista O.S. com filtros
PATCH /api/service-orders/:id Atualiza O.S.
POST /api/service-orders/:id/assign Atribui O.S. a técnico
POST /api/upload-pacote Recebe pacote ZIP do mobile
GET /api/packages/:id Retorna dados do pacote
POST /api/packages/:id/validate Aprova/rejeita pacote
POST /api/packages/:id/forward Encaminha para Auto Relatórios
POST /api/callback/report-completed Callback do Auto Relatórios
GET /api/dashboard/kpis Retorna KPIs consolidados

5.4 Fluxo de Integração

1. Upload de Pacote (Mobile → Gerenciador):

POST /api/upload-pacote
  • Headers: Authorization: Bearer {jwt}
  • Body: multipart/form-data com arquivo ZIP
  • Response: { "package_id": "uuid", "status": "received" }

2. Encaminhamento para Auto Relatórios:

POST https://auto-relatorios.maffeng.com/api/generate
  • Headers: Authorization: Bearer {jwt}
  • Body: { "package_id": "uuid", "template_id": "template-001" }
  • Response: { "job_id": "uuid", "status": "processing" }

3. Callback de Conclusão:

POST /api/callback/report-completed
  • Headers: X-Webhook-Secret: {secret}
  • Body: { "job_id": "uuid", "package_id": "uuid", "report_url": "..." }
  • Sistema atualiza status da O.S. para "Relatório Concluído"

9. Riscos e Mitigações

Risco Probabilidade Impacto Mitigação
Complexidade de integração com mobile maior que esperado MÉDIA ALTO Definir contrato de API detalhado antes do desenvolvimento. Testes de integração desde o início.
Performance degradada com grande volume de fotos MÉDIA ALTO Compressão de imagens no upload. Lazy loading na galeria. CDN para servir assets.
Validação de Excel com formatos inconsistentes ALTA MÉDIO Fornecer template rígido. Validação robusta com mensagens claras de erro.
Falha na integração com TM Auto Relatórios BAIXA CRÍTICO Sistema de retry automático. Fila de processamento com persistência. Monitoramento 24/7.
Usuários resistentes à mudança de processo MÉDIA MÉDIO Onboarding estruturado. Documentação clara. Suporte dedicado nas primeiras semanas.
Custos de Supabase Storage excedendo orçamento MÉDIA MÉDIO Monitorar uso constantemente. Política de limpeza de arquivos antigos. Compressão agressiva.
Bugs críticos em produção após lançamento MÉDIA ALTO Beta privado extensivo. Rollout gradual. Feature flags para rollback rápido. Sentry configurado.

9.1 Plano de Contingência

Cenário Crítico: Sistema indisponível por mais de 2 horas

Ações:

  1. Ativar página de status para comunicação com usuários
  2. Técnicos continuam trabalho offline no app mobile
  3. Pacotes são armazenados localmente e sincronizados após restore
  4. Backup de emergência via Supabase ativado (RTO < 4h)
  5. Comunicação proativa com clientes afetados

10.3 Contratos de API (Resumo)

Mobile → Gerenciador

POST /api/upload-pacote

Request: multipart/form-data com ZIP

Response: { package_id, status, message }

Autenticação: Bearer Token (JWT)

Gerenciador → Auto Relatórios

POST /api/generate

Request: { package_id, template_id, contract_id }

Response: { job_id, status, eta }

Autenticação: API Key (server-to-server)

Auto Relatórios → Gerenciador (Callback)

POST /api/callback/report-completed

Request: { job_id, package_id, report_url, status }

Response: { acknowledged: true }

Autenticação: Webhook Secret (header)

12. Glossário

Termo Definição
O.S. Ordem de Serviço - Documento que autoriza e especifica um trabalho técnico a ser executado
Pacote de Levantamento Arquivo ZIP contendo fotos, JSON com dados estruturados e metadados de uma vistoria
Validação Processo de aprovação ou rejeição de um pacote de levantamento pelo gerente
SLA Service Level Agreement - Prazo contratual para conclusão de uma O.S.
Callback Requisição HTTP enviada por um sistema para notificar outro sobre conclusão de processo
JWT JSON Web Token - Padrão de autenticação baseado em tokens
RLS Row Level Security - Controle de acesso a dados no nível de linha do banco
Supabase Plataforma BaaS (Backend as a Service) baseada em PostgreSQL
KPI Key Performance Indicator - Indicador chave de desempenho
MVP Minimum Viable Product - Versão mínima funcional do produto
Endpoint URL de uma API que recebe requisições HTTP
Webhook Callback HTTP automático quando um evento ocorre em outro sistema
