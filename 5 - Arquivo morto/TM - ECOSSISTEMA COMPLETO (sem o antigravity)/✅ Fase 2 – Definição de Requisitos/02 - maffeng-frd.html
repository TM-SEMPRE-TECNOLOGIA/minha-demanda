RF-001 a RF-007: Gestão de Ordens de Serviço

RF-001 CRÍTICA
Importação em Lote de O.S. via Excel
Descrição
O sistema deve permitir que o gerente importe múltiplas ordens de serviço através de uma planilha Excel (.xlsx), validando automaticamente a estrutura e os dados obrigatórios antes de confirmar a importação.
Fluxo Principal
1
Upload de Arquivo
Gerente acessa módulo de importação e faz upload de arquivo .xlsx
2
Validação Estrutural
Sistema valida colunas obrigatórias e formato dos dados
3
Preview de Dados
Exibe tabela com preview das O.S. a serem importadas
4
Confirmação
Gerente confirma importação após revisar dados
5
Persistência
Sistema cria registros no banco de dados com status "Pendente"
6
Feedback
Notificação de sucesso com resumo da importação
Campos Obrigatórios
  • numero_os - Número único da ordem de serviço (string, máx 50 caracteres)
  • endereco - Endereço completo do local (string, máx 255 caracteres)
  • cliente - Nome do cliente/contratante (string, máx 100 caracteres)
  • prazo - Data limite de conclusão (date, formato YYYY-MM-DD)
  • tipo_servico - Categoria do serviço (enum: vistoria, manutenção, laudo)
Campos Opcionais
  • observacoes - Observações adicionais (text)
  • prioridade - Nível de prioridade (enum: baixa, média, alta, crítica)
  • valor - Valor do serviço (decimal 10,2)
  • ambientes - Lista de ambientes a vistoriar (text, separado por vírgula)
Validações
  • Arquivo deve ser formato .xlsx válido
  • Número de O.S. deve ser único no sistema
  • Prazo não pode ser data passada
  • Campos obrigatórios não podem estar vazios
  • Endereço deve ter pelo menos 10 caracteres
  • Máximo de 1000 O.S. por importação
Tratamento de Erros
  • Arquivo inválido - "Formato de arquivo não suportado. Use .xlsx"
  • Colunas faltando - "Planilha incompleta. Campos obrigatórios: [lista]"
  • Número duplicado - "O.S. [numero] já existe no sistema"
  • Dados inválidos - Destacar linhas com erro em vermelho no preview
  • Limite excedido - "Máximo de 1000 O.S. por importação. Divida o arquivo."
Exemplo de Código (Validação)
async function validateExcelData(rows) { const errors = []; const duplicates = new Set(); for (let i = 0; i < rows.length; i++) { const row = rows[i]; // Validar campos obrigatórios if (!row.numero_os || !row.endereco || !row.cliente || !row.prazo) { errors.push({ line: i + 2, error: 'Campos obrigatórios faltando' }); } // Validar duplicatas internas if (duplicates.has(row.numero_os)) { errors.push({ line: i + 2, error: 'Número de O.S. duplicado na planilha' }); } duplicates.add(row.numero_os); // Validar prazo const prazoDate = new Date(row.prazo); if (prazoDate < new Date()) { errors.push({ line: i + 2, error: 'Prazo não pode ser data passada' }); } } return errors; }
Critérios de Aceitação
  • ✓ Gerente consegue importar 100 O.S. válidas em menos de 5 segundos
  • ✓ Sistema identifica e reporta todas as linhas com erro
  • ✓ Preview exibe dados formatados corretamente
  • ✓ Confirmação cria todos os registros no banco com status correto
  • ✓ Mensagem de sucesso exibe quantidade de O.S. importadas
RF-002 CRÍTICA
Validação de Campos Obrigatórios
Descrição
O sistema deve validar automaticamente todos os campos obrigatórios durante a importação de O.S., impedindo a criação de registros incompletos e fornecendo feedback claro sobre campos faltantes ou inválidos.
Regras de Validação por Campo
Campo Tipo Validação Mensagem de Erro
numero_os String Não vazio, máx 50 chars, único "Número da O.S. é obrigatório e deve ser único"
endereco String Mín 10 chars, máx 255 "Endereço deve ter entre 10 e 255 caracteres"
cliente String Não vazio, máx 100 chars "Nome do cliente é obrigatório"
prazo Date Data válida, futura "Prazo deve ser uma data futura válida"
tipo_servico Enum Valor em lista permitida "Tipo de serviço inválido. Use: vistoria, manutenção ou laudo"
Critérios de Aceitação
  • ✓ Validação ocorre antes de salvar no banco de dados
  • ✓ Mensagens de erro são claras e específicas
  • ✓ Sistema destaca campos com erro na interface
  • ✓ Validação de unicidade consulta banco em tempo real
RF-003 ALTA
Preview de Importação
Descrição
Antes de confirmar a importação, o sistema deve exibir uma tabela interativa com preview de todas as O.S. que serão importadas, permitindo revisão visual e identificação de problemas.
Elementos da Interface
  • Tabela responsiva com scroll horizontal em mobile
  • Colunas: Número O.S., Endereço, Cliente, Prazo, Tipo, Status de Validação
  • Linhas com erro destacadas em vermelho
  • Ícone de alerta ao lado de campos inválidos
  • Tooltip com detalhes do erro ao passar mouse sobre ícone
  • Contadores: "X O.S. válidas | Y com erro"
  • Botões: "Corrigir Erros", "Cancelar", "Confirmar Importação"
Critérios de Aceitação
  • ✓ Preview carrega em menos de 2 segundos para 100 O.S.
  • ✓ Erros são visualmente destacados e explicados
  • ✓ Botão "Confirmar" só habilitado se não houver erros
  • ✓ Gerente pode cancelar e corrigir planilha antes de confirmar
RF-004 MÉDIA
Criação Manual de O.S. Individual
Descrição
O sistema deve permitir que o gerente crie uma ordem de serviço individual através de um formulário web, útil para casos urgentes ou correções pontuais.
Elementos do Formulário
  • Campo texto: Número da O.S. (validação de unicidade em tempo real)
  • Campo texto: Endereço completo
  • Campo texto: Nome do cliente
  • Campo date picker: Prazo de conclusão
  • Campo select: Tipo de serviço
  • Campo select: Prioridade (opcional)
  • Campo textarea: Observações (opcional)
  • Campo numérico: Valor do serviço (opcional)
  • Campo texto: Lista de ambientes (opcional)
Validações em Tempo Real
  • Número de O.S. verifica duplicatas ao sair do campo (onBlur)
  • Endereço valida tamanho mínimo (10 chars) ao digitar
  • Prazo impede seleção de datas passadas
  • Campos obrigatórios marcados com asterisco vermelho
  • Botão "Salvar" desabilitado se houver erros de validação
Critérios de Aceitação
  • ✓ Formulário responsivo em mobile, tablet e desktop
  • ✓ Validação ocorre sem reload da página
  • ✓ Mensagens de erro aparecem abaixo de cada campo
  • ✓ Após salvar, gerente é redirecionado para detalhes da O.S. criada
  • ✓ Notificação de sucesso exibida por 3 segundos
RF-005 MÉDIA
Edição de O.S. Antes de Atribuição
Descrição
O sistema deve permitir edição de ordens de serviço que ainda não foram atribuídas a técnicos, possibilitando correção de dados antes da distribuição.
Regras de Negócio
  • Apenas O.S. com status "Pendente" podem ser editadas
  • O.S. atribuídas, em execução ou concluídas são somente leitura
  • Todos os campos, exceto número de O.S., podem ser alterados
  • Histórico de alterações deve ser registrado automaticamente
  • Data/hora da última modificação e usuário responsável são salvos
Fluxo de Edição
1
Acesso
Gerente clica em "Editar" na lista de O.S. pendentes
2
Validação de Status
Sistema verifica se O.S. ainda está "Pendente"
3
Exibição do Formulário
Campos preenchidos com dados atuais da O.S.
4
Alteração
Gerente modifica campos necessários
5
Validação
Sistema valida novos dados (mesmas regras de criação)
6
Persistência
Atualiza registro e cria entrada no histórico
Critérios de Aceitação
  • ✓ Botão "Editar" visível apenas para O.S. pendentes
  • ✓ Tentativa de editar O.S. atribuída exibe mensagem de bloqueio
  • ✓ Histórico registra campo alterado, valor anterior e novo
  • ✓ Alterações refletidas imediatamente na listagem
RF-006 CRÍTICA
Bloqueio de Exclusão de O.S. em Andamento
Descrição
O sistema deve impedir a exclusão de ordens de serviço que já foram atribuídas a técnicos ou estão em execução, garantindo integridade do fluxo operacional e rastreabilidade.
Regras de Exclusão
  • PERMITIDO: Exclusão de O.S. com status "Pendente" (não atribuída)
  • BLOQUEADO: O.S. com status "Atribuída"
  • BLOQUEADO: O.S. com status "Em Execução"
  • BLOQUEADO: O.S. com status "Aguardando Validação"
  • BLOQUEADO: O.S. com status "Concluída"
  • BLOQUEADO: O.S. que já possuem pacotes de levantamento associados
Comportamento da Interface
  • Botão "Excluir" visível apenas para O.S. pendentes
  • Botão desabilitado (cinza) para O.S. bloqueadas
  • Tooltip explicativo ao passar mouse sobre botão desabilitado
  • Modal de confirmação para exclusões permitidas: "Tem certeza? Esta ação não pode ser desfeita."
  • Após exclusão bem-sucedida, linha removida da tabela com animação
Mensagens de Erro
  • O.S. Atribuída: "Esta O.S. já foi atribuída a um técnico e não pode ser excluída."
  • O.S. em Execução: "Esta O.S. está em execução e não pode ser excluída."
  • Possui Pacotes: "Esta O.S. possui levantamentos fotográficos e não pode ser excluída."
Critérios de Aceitação
  • ✓ Tentativa de exclusão de O.S. bloqueada retorna erro 403
  • ✓ Interface previne ação antes de chamar API
  • ✓ Exclusão permitida remove registro do banco permanentemente
  • ✓ Histórico de exclusões é registrado em log de auditoria
RF-007 ALTA
Histórico Completo de Alterações
Descrição
O sistema deve registrar automaticamente todas as alterações realizadas em cada ordem de serviço, criando um histórico auditável e rastreável de modificações.
Eventos Rastreados
Evento Dados Registrados Exibição
Criação Data/hora, usuário, método (importação/manual) "Criada por [usuário] em [data hora]"
Edição Data/hora, usuário, campo alterado, valor anterior, valor novo "[campo] alterado de '[antigo]' para '[novo]' por [usuário]"
Atribuição Data/hora, usuário gerente, técnico atribuído "Atribuída ao técnico [nome] por [gerente]"
Reatribuição Data/hora, técnico anterior, novo técnico, motivo "Reatribuída de [técnico1] para [técnico2]"
Mudança de Status Data/hora, status anterior, novo status, ator "Status alterado de [anterior] para [novo]"
Upload de Pacote Data/hora, técnico, tamanho do arquivo, ID do pacote "Pacote enviado por [técnico] ([tamanho])"
Estrutura de Dados (JSON)
{ "os_id": "uuid", "timestamp": "2025-11-11T14:30:00Z", "event_type": "field_update", "user_id": "uuid", "user_name": "Ana Rodrigues", "field_changed": "prazo", "old_value": "2025-11-15", "new_value": "2025-11-20", "metadata": { "ip_address": "192.168.1.100", "user_agent": "Mozilla/5.0..." } }
Visualização na Interface
  • Timeline vertical com eventos ordenados cronologicamente (mais recente no topo)
  • Ícones diferentes para cada tipo de evento
  • Cores: Verde (criação/atribuição), Azul (edição), Amarelo (reatribuição)
  • Filtro por tipo de evento e período
  • Exportação do histórico em formato PDF ou CSV
Critérios de Aceitação
  • ✓ Todo evento registrado em menos de 100ms
  • ✓ Histórico é imutável (não pode ser editado ou excluído)
  • ✓ Timeline carrega em menos de 1 segundo
  • ✓ Dados do histórico persistem mesmo após exclusão da O.S.

RF-008 a RF-013: Distribuição e Atribuição

RF-008 CRÍTICA
Atribuição de O.S. para Técnicos
Descrição
O sistema deve permitir que o gerente atribua ordens de serviço pendentes a técnicos cadastrados no sistema, alterando automaticamente o status e notificando o técnico via app mobile.
Fluxo de Atribuição
1
Seleção da O.S.
Gerente visualiza lista de O.S. pendentes e seleciona uma
2
Escolha do Técnico
Sistema exibe lista de técnicos disponíveis com indicador de carga
3
Confirmação
Gerente confirma atribuição (modal de confirmação)
4
Atualização de Status
Sistema altera status para "Atribuída" e salva ID do técnico
5
Notificação
Sistema envia notificação push para app mobile do técnico
6
Sincronização
O.S. aparece na lista do técnico no app (offline-first)
Dados do Técnico Exibidos
  • Nome completo
  • Foto de perfil (avatar)
  • Especialização (tipo de serviço que realiza)
  • Carga atual: "X O.S. ativas"
  • Última localização conhecida (para otimizar logística)
  • Status: Disponível, Ocupado, Offline
Regras de Negócio
  • Apenas O.S. com status "Pendente" podem ser atribuídas
  • Apenas técnicos ativos podem receber atribuições
  • Sistema registra data/hora da atribuição
  • Histórico de atribuição fica vinculado à O.S.
  • Gerente pode adicionar observações para o técnico
Critérios de Aceitação
  • ✓ Atribuição completa em menos de 3 segundos
  • ✓ Técnico recebe notificação em até 10 segundos
  • ✓ Status da O.S. atualizado instantaneamente na listagem
  • ✓ O.S. sincronizada com app mobile do técnico
RF-009 ALTA
Atribuição Múltipla de O.S.
Descrição
O sistema deve permitir que o gerente selecione múltiplas ordens de serviço e as atribua simultaneamente a um ou mais técnicos, otimizando o processo de distribuição.
Modos de Atribuição Múltipla
Modo Comportamento Caso de Uso
N para 1 Várias O.S. para um único técnico Técnico especializado recebe lote de O.S. similares
N para N Distribuição equilibrada entre vários técnicos Gerente seleciona 10 O.S. e 2 técnicos, sistema divide 5/5
Por Região Atribuição automática baseada em endereço O.S. geograficamente próximas vão para mesmo técnico
Interface de Seleção
  • Checkbox na primeira coluna de cada linha da tabela
  • Checkbox no header para "Selecionar Todas"
  • Contador de seleção: "X O.S. selecionadas"
  • Botão "Atribuir Selecionadas" aparece quando há seleção
  • Modal com lista de técnicos e opções de distribuição
Critérios de Aceitação
  • ✓ Atribuição em lote de 50 O.S. completa em menos de 10 segundos
  • ✓ Sistema valida disponibilidade de cada técnico antes de atribuir
  • ✓ Todos os técnicos recebem notificações simultâneas
  • ✓ Falha em uma atribuição não bloqueia as demais (atomic operations)
RF-010 MÉDIA
Exibição de Carga de Trabalho do Técnico
Descrição
O sistema deve exibir a carga de trabalho atual de cada técnico durante o processo de atribuição, ajudando o gerente a distribuir O.S. de forma equilibrada.
Indicadores de Carga
  • O.S. Ativas: Quantidade de O.S. atribuídas + em execução
  • Prazo Médio: Tempo médio até vencimento das O.S. atuais
  • Taxa de Conclusão: % de O.S. concluídas no prazo (últimos 30 dias)
  • Disponibilidade: Estimativa de capacidade restante
  • Última Atividade: Data/hora do último envio de pacote
Visualização
  • Barra de progresso visual: Verde (baixa carga), Amarelo (média), Vermelho (alta)
  • Badge numérico: "12 O.S." ao lado do nome do técnico
  • Tooltip com detalhamento ao passar mouse
  • Ordenação padrão: técnicos com menor carga aparecem primeiro
Critérios de Aceitação
  • ✓ Indicadores atualizam em tempo real ao atribuir nova O.S.
  • ✓ Cálculo de carga considera apenas O.S. ativas (não concluídas)
  • ✓ Sistema sugere técnico com menor carga por padrão
RF-011 ALTA
Reatribuição de O.S. Entre Técnicos
Descrição
O sistema deve permitir que o gerente reatribua uma ordem de serviço de um técnico para outro, útil em casos de sobrecarga, férias ou emergências.
Regras de Reatribuição
  • PERMITIDO: Reatribuir O.S. com status "Atribuída" ou "Em Execução"
  • BLOQUEADO: O.S. com status "Aguardando Validação" (pacote já enviado)
  • BLOQUEADO: O.S. concluídas ou rejeitadas
  • OBRIGATÓRIO: Motivo da reatribuição (campo texto)
  • NOTIFICAÇÃO: Ambos técnicos (anterior e novo) são notificados
Fluxo de Reatribuição
1
Acesso
Gerente clica em "Reatribuir" na O.S. desejada
2
Validação
Sistema verifica se reatribuição é permitida
3
Seleção
Modal exibe lista de técnicos (exceto o atual)
4
Motivo
Gerente informa motivo obrigatório da reatribuição
5
Confirmação
Sistema atualiza técnico responsável e registra no histórico
6
Notificações
Técnico anterior: "O.S. X removida". Novo técnico: "Nova O.S. atribuída"
Motivos Comuns (Sugestões)
  • Técnico sobrecarregado
  • Técnico de férias/afastado
  • Especialização específica necessária
  • Otimização logística (proximidade geográfica)
  • Solicitação do cliente
  • Outro (campo livre)
Critérios de Aceitação
  • ✓ Reatribuição registrada no histórico com motivo
  • ✓ O.S. removida do app do técnico anterior imediatamente
  • ✓ O.S. aparece no app do novo técnico em até 10 segundos
  • ✓ Tentativa de reatribuir O.S. bloqueada exibe mensagem clara

RF-013 CRÍTICA
Sincronização com App Mobile Offline
Descrição
O sistema deve sincronizar automaticamente as ordens de serviço atribuídas com o aplicativo mobile do técnico, garantindo que os dados estejam disponíveis offline para trabalho em campo.
Arquitetura de Sincronização
1
Atribuição no Web
Gerente atribui O.S. via TM Gerenciador
2
Persistência
Dados salvos no Supabase com flag "sync_pending"
3
Push Notification
App mobile recebe notificação de nova O.S.
4
Download de Dados
App faz GET /api/os/:id para baixar detalhes
5
Armazenamento Local
Dados persistidos em SQLite local (offline-first)
6
Disponível Offline
Técnico pode acessar O.S. mesmo sem internet
Dados Sincronizados
  • Informações completas da O.S. (número, endereço, prazo, observações)
  • Lista de ambientes a vistoriar
  • Templates de checklist (se aplicável)
  • Histórico de interações anteriores
  • Coordenadas GPS do endereço para navegação
Estratégia de Conflito
  • Última escrita vence: Se O.S. for modificada no web e app simultaneamente, última atualização prevalece
  • Merge inteligente: Fotos capturadas offline sempre preservadas
  • Versionamento: Cada sincronização incrementa campo "version"
  • Notificação de conflito: Gerente alertado se houver conflitos críticos
Indicadores de Sincronização
  • Ícone de "nuvem" verde: Sincronizado
  • Ícone de "nuvem com seta": Sincronizando
  • Ícone de "nuvem offline": Disponível offline, aguardando conexão
  • Timestamp da última sincronização: "Atualizado há 5 min"
Critérios de Aceitação
  • ✓ Sincronização inicial completa em até 30 segundos (conexão 4G)
  • ✓ App funciona 100% offline após sincronização inicial
  • ✓ Fotos capturadas offline sincronizam automaticamente quando houver conexão
  • ✓ Sistema de fila garante ordem de sincronização (FIFO)
  • ✓ Retry automático em caso de falha de rede

RF-014 a RF-024: Recebimento e Validação de Pacotes

RF-014 CRÍTICA
Recebimento de Pacotes ZIP via REST
Descrição
O sistema deve expor um endpoint REST seguro para receber pacotes ZIP enviados pelo aplicativo mobile, contendo fotos, JSON com dados estruturados e metadados do levantamento fotográfico.
Especificação do Endpoint
POST /api/upload-pacote Content-Type: multipart/form-data Authorization: Bearer {jwt_token} Request Body: - file: arquivo ZIP (binary) - os_id: UUID da ordem de serviço - tecnico_id: UUID do técnico - metadata: JSON com informações adicionais Response (201 Created): { "success": true, "package_id": "uuid-do-pacote", "status": "received", "message": "Pacote recebido com sucesso", "files_count": 25, "total_size": "45.2 MB", "received_at": "2025-11-11T14:30:00Z" } Response (400 Bad Request): { "success": false, "error": "invalid_file", "message": "Arquivo ZIP corrompido ou inválido" }
Validações no Upload
  • Arquivo deve ser formato ZIP válido
  • Tamanho máximo: 100 MB
  • Token JWT válido e não expirado
  • O.S. deve existir e estar atribuída ao técnico autenticado
  • Técnico deve ter permissão para enviar pacote para esta O.S.
  • O.S. não pode já ter pacote validado (evitar duplicatas)
Processamento Assíncrono
1
Upload Completo
Arquivo ZIP recebido e salvo temporariamente
2
Resposta Imediata
API retorna 201 com package_id para app mobile
3
Job Background
Worker inicia processamento assíncrono do ZIP
4
Extração

RF-015 CRÍTICA
Validação de Integridade do Arquivo
Descrição
O sistema deve validar a integridade do arquivo ZIP recebido usando checksum (hash MD5 ou SHA256), garantindo que o arquivo não foi corrompido durante a transferência.
Implementação de Checksum
// App mobile calcula hash antes de enviar const fileHash = await calculateSHA256(zipFile); // Envia no header da requisição headers: { 'X-File-Checksum': fileHash, 'X-File-Size': fileSize } // Servidor valida após receber const receivedHash = calculateSHA256(receivedFile); if (receivedHash !== requestHeaders['X-File-Checksum']) { return res.status(400).json({ error: 'checksum_mismatch', message: 'Arquivo corrompido durante transferência' }); }
Validações Adicionais
  • Tamanho do arquivo recebido = tamanho declarado no header
  • Arquivo pode ser descompactado sem erros
  • Estrutura interna do ZIP está correta (pastas esperadas)
  • Todos os arquivos internos são válidos (fotos legíveis)
Tratamento de Erros
  • Checksum inválido: "Arquivo corrompido. Tente enviar novamente."
  • ZIP corrompido: "Não foi possível descompactar o arquivo."
  • Tamanho divergente: "Tamanho do arquivo não corresponde ao declarado."
Critérios de Aceitação
  • ✓ Validação de checksum completa em menos de 1 segundo
  • ✓ Arquivo corrompido rejeitado antes de processar
  • ✓ App mobile pode reenviar automaticamente em caso de falha

RF-027 CRÍTICA
Lista de O.S. em Risco de Atraso
Descrição
O sistema deve exibir uma lista destacada de ordens de serviço com risco de atraso (SLA < 20% do prazo restante), permitindo ação proativa do gerente.
Cálculo de Risco
// Lógica de cálculo de risco function calculateRisk(os: ServiceOrder): RiskLevel { const now = new Date(); const deadline = new Date(os.prazo); const created = new Date(os.created_at); const totalTime = deadline.getTime() - created.getTime(); const elapsed = now.getTime() - created.getTime(); const remaining = deadline.getTime() - now.getTime(); const percentRemaining = (remaining / totalTime) * 100; if (percentRemaining < 0) return 'vencido'; // Vermelho crítico if (percentRemaining < 20) return 'critico'; // Vermelho if (percentRemaining < 40) return 'alto'; // Laranja if (percentRemaining < 60) return 'medio'; // Amarelo return 'baixo'; // Verde }
Visualização
  • Widget no dashboard com título "⚠️ O.S. em Risco"
  • Lista com no máximo 10 O.S. mais críticas
  • Cada item mostra: Número O.S., Endereço, Técnico, Prazo restante
  • Indicador visual de risco: Vermelho (crítico), Laranja (alto), Amarelo (médio)
  • Botão "Ver Todas" leva para lista completa filtrada
  • Ordenação: O.S. vencidas primeiro, depois por % restante crescente
Alertas Automáticos
  • Email para gerente quando O.S. entra em risco crítico
  • Notificação no dashboard (badge vermelho no ícone de sino)
  • Alerta para técnico responsável 48h antes do vencimento
Critérios de Aceitação
  • ✓ Lista atualiza em tempo real
  • ✓ Cálculo de risco preciso com base no prazo
  • ✓ Alertas enviados no momento correto
  • ✓ Gerente pode tomar ação (reatribuir, priorizar) direto da lista
